# 명령창 파일 드롭

컴퓨터의 파일을 앱 창 어디에 놓아도 하단 명령창의 기존 첨부 목록에 추가된다. 여러 파일과 나중에 추가한 파일도 같은 목록에 남는다. 드롭 뒤에는 명령 입력창에 포커스를 두므로 바로 글을 쓸 수 있다. 파일은 제거 가능한 칩으로 붙고, 보내기 버튼이나 Enter로 명령을 보내기 전에는 에이전트에게 전송하지 않는다.

## 이번 변경

이전 구현은 하단 작성 줄에서만 파일을 받았다. 창 대부분에서는 금지 커서가 나타났고, 화면 가운데에 놓은 파일은 아무 반응 없이 사라졌다. 창으로 파일을 끌어다 놓는 동작을 지원하려면 작은 작성 줄을 겨냥할 필요가 없어야 하므로 드롭 영역을 창 전체로 넓혔다. 대화 기록 위에 놓은 파일도 첨부한다. 잘못 붙인 파일은 칩의 제거 버튼으로 지울 수 있다.

안내는 작성 줄에 그대로 두고 문구를 "창 어디에 놓아도 명령에 첨부됩니다"로 바꿨다. 화면 가운데에서 드래그해도 받을 위치와 보낼 대상을 미리 보여 준다. 전체 창을 덮거나 어둡게 만들지 않아 사무실을 계속 읽을 수 있다.

## 영역과 안내

파일이 창 안에 들어오면 작성 줄에 초록 테두리와 안내가 나타난다. 보낼 대상과 파일당 50 MB 제한도 함께 표시한다. 대상 선택값은 바꾸지 않는다.

안내는 입력창 위에 겹쳐 표시해 드래그 중에도 배치가 움직이지 않는다. 애니메이션은 없다. 600px 이하에서는 드롭 안내와 테두리를 숨긴다. 390px의 평상시 화면과 파일 드래그 화면은 같은 이미지이며, 기존 첨부 칩의 스크롤 배치를 유지한다.

페이지를 막는 대화상자가 열려 있을 때는 창 전체에서 첨부를 중단한다. 앱의 `aria-modal="true"` 대화상자와 열린 네이티브 `dialog`가 기준이다. 대화상자 내부, 배경, 작성 줄 모두 안내를 숨기고 금지 커서를 쓰며, 드롭해도 첨부하거나 입력창으로 포커스를 옮기지 않는다. 대화상자를 닫으면 다시 창 전체에서 받는다. 이때도 파일이 브라우저에서 열리는 기본 동작은 막는다.

텍스트와 링크의 기본 동작은 그대로 둔다. 창 안의 요소 사이를 이동할 때는 안내를 유지한다. 창 이탈, Esc, 포커스 상실, 드롭, dragend, 페이지 숨김에서 강조 표시를 지운다. 운영체제가 취소 이벤트를 보내지 않는 경우에는 마지막 dragover 이후 700ms에 지운다.

## 첨부와 접근성

웹에서는 종이클립과 이미지 붙여넣기가 쓰는 `UploadQueue`를 그대로 사용한다. 동시 업로드 3개, 50 MB 제한, 진행률, 오류, 재시도와 전송 대기를 공유한다. 용량 초과 파일도 기존과 같은 제거 가능한 오류 칩으로 남는다.

데스크톱에서는 드롭 파일을 `FileReader`로 데이터 URL로 읽어 기존 칩에 추가한다. 50 MB 초과 파일은 읽지 않고 이유를 표시한다. 파일을 읽는 동안에는 Enter와 보내기 버튼으로 전송하지 않는다. 폴더는 내부를 탐색하지 않고 거절하며, 함께 놓은 일반 파일은 추가한다.

추가한 파일 수와 거절 이유를 `role="status"`, `aria-live="polite"`로 알린다. 거절 이유는 화면에도 남긴다. 알림은 포커스를 옮기지 않으며, 드롭 동작 자체만 입력창에 포커스를 둔다. 키보드 사용자는 기존 파일 첨부 버튼을 계속 쓴다.

데모는 `?fakeUpload=mixed`에서 첫 파일을 준비 완료, 둘째 파일을 재시도 가능한 오류로 보여 준다. 데모 대화 기록에는 업로드 파일의 크기와 MIME 형식도 반영한다. preload와 서버 계약은 변경하지 않았다.

## 검증

드롭 단위·컴포넌트 테스트 23개를 포함한 렌더러 테스트 516개가 통과했다. TypeScript, 계약 검사와 서버용 웹 빌드도 통과했다. [변이 결과](mutation-results.json)는 34개 오류를 모두 검출했다. 작성 줄로만 영역을 되돌리는 오류, 창 진입 안내 누락, 대화상자 뒤 첨부와 취소 뒤 강조 잔류도 검출한다. `tests/`는 수정하지 않았다.

[브라우저 검증 기록](browser-audit.json)에는 실제 선택 텍스트 드래그, 화면 가운데와 대화 기록 위 드롭, 파일 취소, 드롭 뒤 포커스, 칩 제거, 대화상자 차단과 닫은 뒤 복구, 재시도, 키보드 첨부, 이미지 붙여넣기, Enter 전송과 대화 기록 확인이 담겨 있다. 파일 드래그는 합성 `DataTransfer`로 재현한다. Chromium은 이 객체의 `dropEffect`를 변경하지 않으므로 커서 지정은 컴포넌트 테스트에서 검증한다.

1440과 390의 [평상시](captures/idle-1440.png), [파일 드래그](captures/file-over-1440.png), [두 파일 첨부](captures/two-files-1440.png) 캡처를 다시 만들고 6장을 직접 확인했다. 드래그 위치는 작성 줄 밖인 창의 정중앙이다. 검증 기록에 좌표와 작성 줄 밖 여부를 남긴다. 각 상태의 `-390.png`도 같은 폴더에 있다. 1440에서는 사무실을 가리지 않고 하단 목적지가 보이며, 390에서는 평상시와 드래그 화면이 같고 첨부 칩의 기존 스크롤 배치를 유지한다.

PNG 6장은 저장소의 기존 `.gitignore` 규칙에 따라 디스크에만 남는다. 캡처 도구로 다시 만들 수 있다.

재실행할 때 `VT_WRAPPER`에 승인된 CPU 실행기 경로를 지정한다. 다음 명령을 하나씩 실행한다.

```sh
bash "$VT_WRAPPER" -- npx tsc --noEmit -p tsconfig.web.json
node src/renderer/tools/check-contract.mjs
bash "$VT_WRAPPER" run --config src/renderer/tools/vitest.config.ts
bash "$VT_WRAPPER" -- npm run build:web
COMMAND_DROP_VITEST_WRAPPER="$VT_WRAPPER" bash "$VT_WRAPPER" -- node src/renderer/tools/mutate-command-drop.mjs
bash "$VT_WRAPPER" -- node src/renderer/tools/capture-command-drop.mjs
```

캡처 도구는 가짜 브리지를 쓰는 개발 페이지를 5196에서 열고, 헤드리스 브라우저 하나로 검사한다. 종료 시 서버와 브라우저를 닫고 임시 프로필을 지운다. 실제 데스크톱 앱과 실제 서버는 실행하지 않았다. 데모에서 명령을 보낸 뒤 발생하는 기존 활동 피드의 중복 React key `1003` 경고는 이번 변경 범위에서 수정하지 않았다.
