**승인 구분** · CLI 명령·파일 작업의 **실행 권한 승인**은 바이패스합니다. 작업의 **검수**, 보고서의 **결과 승인**, 선택 기능인 **계획 승인**은 별개이며 유지합니다. 실행 승인 대기 화면과 승인 대기 타이머는 만들지 않습니다.

## 1. 개요

욱채 프로그램은 대표(사용자)가 메인 에이전트에게 명령을 내리면, 메인 에이전트가 프로젝트별 AI 팀(Claude·Codex 세션)을 꾸리고 지휘해 결과를 정리·보고하는 AI 스튜디오 운영 PC 프로그램입니다. 프로그램이 내부에서 Claude Code CLI와 Codex CLI를 실행합니다. 팀원은 이름·역할·설정·이력을 유지하는 개체이며, 작업마다 실행 세션을 연결하거나 교체합니다. 팀은 일반적인 개발 회사처럼 일합니다. 프로듀서가 지시를 작업으로 쪼개 팀원에게 배정하고, 팀원은 각자의 작업 공간에서 일한 뒤 검수를 거쳐 결과를 합치며, 결과는 보고서로 대표에게 올라갑니다.

| 핵심 기능 | 내용 | 위치 |
|---|---|---|
| 스튜디오 모니터링 | 프로젝트별 팀 구성(AI 종류·노력치·역할)과 팀원별 상태·작업·진행도를 시각적으로 확인 | 프로젝트 탭 |
| 명령·보고 체계 | 대표 → 메인 에이전트 → 프로듀서 → 팀원으로 지시하고 반대 방향으로 보고. 보고서마다 결과 승인·수정 요청 | 하단 명령창, 문서함 탭 |
| 보고 문서 보관 | 보고서를 프로젝트·지시·회차별로 보관하고 검색 | 문서함 탭 |
| 결과 시뮬레이션 | 진행 중인 지시가 끝났을 때의 결과를 프로젝트 실제 UI로 짧게 플레이 | 시뮬레이션 탭 |
| 운영 통제 | 긴급 정지(전역 단축키), 앱 도구 권한, 작업 공간 운영 규칙, 활동 기록. 실행 권한은 승인 없이 바이패스 | 상단 바, 트레이, 운영 설정 탭 |

## 2. 용어 정의

| 용어 | 정의 |

| CLI 세션 | 특정 팀원·프로젝트·업무에 연결한 대화 문맥. 작업별 새 세션이 기본이고, 같은 작업의 다음 턴은 해당 세션을 이어서 실행 |
| 프로듀서 | 프로젝트마다 반드시 1명 있는 팀 책임자. 일반 개발사의 PM·PD |
| 역할 | 팀원이 맡는 직무(기획, 개발, QA 등). 지침·스킬·기본 설정의 묶음 |
| 지시 | 대표가 명령창으로 내린 명령 1건. 일반 개발사의 요청·에픽 |
| 작업 | 프로듀서가 지시를 쪼개 팀원 1명에게 배정한 일. 일반 개발사의 티켓·태스크 |
| 단계 | 팀원이 작업을 진행하며 나눈 체크리스트 항목. 진행도 계산 기준 |
| 검수 | 작업 결과를 작업자가 아닌 사람이 확인하는 절차. 일반 개발사의 코드 리뷰·QA |
| 작업 공간 | 작업마다 따로 만드는 git 브랜치와 작업 폴더(worktree) |
| 병합 | 검수를 통과한 변경을 기준 브랜치(main)에 합치는 것 |
| 민감 영역 | 기존 보호 구역 목록을 바꾼 명칭. 시스템·개인 파일·비밀 정보·앱 데이터처럼 용도와 접근 이력을 구분할 영역이며, 실행 승인이나 강제 격리를 뜻하지 않음 |
| 노력치 | 팀원 AI가 얼마나 깊게 생각하며 작업할지 정하는 설정값. AI별로 지원하는 단계를 그대로 사용 |
| 스킬 | 에이전트가 특정 업무에 쓰는 기능 묶음. 자동 발동 스킬과 수동 발동 스킬이 있음 |
| 리스트바 | 명령창 왼쪽에서 명령 대상 프로젝트를 고르는 선택 목록 |
| 시뮬레이션 | 진행 중인 지시가 끝났을 때의 예상 결과를 프로젝트 실제 UI로 짧게 플레이해보는 기능 |
| 모의 에이전트 | 개발·테스트용 가짜 팀원. 실제 AI 대신 정해진 시나리오대로 움직임 |
| 앱 도구 | 에이전트가 프로그램 기능(단계 보고, 검수 등록, 작업 배정 등)을 쓰는 통로. 프로그램이 MCP 서버로 제공하며 역할·프로젝트·작업 배정에 따라 호출 권한을 검사 |
| 트레이 | 작업 표시줄(Windows)이나 메뉴 막대(macOS)에 있는 프로그램 아이콘. 창을 닫아도 여기서 계속 실행 |
| 턴 | CLI를 한 번 실행해 끝날 때까지의 단위. 다음 턴은 같은 세션을 이어서(resume) 실행 |

## 3. 개발 차수

기능을 한 번에 다 만들지 않고, 핵심 흐름이 먼저 끝까지 돌아가는 순서로 나눕니다. 실행 권한 승인은 바이패스하되 긴급 정지·상태 보존·앱 도구 권한·활동 기록은 1차에 넣습니다.

| 개발 차수 | 목표 | 포함 범위 |
|---|---|---|
| 1차 | 핵심 흐름(팀 구성 → 지시 → 작업 → 보고)과 운영 통제가 끝까지 돌아가는 버전 | 모의 에이전트(가장 먼저), 로그인, 프로젝트 등록, 팀 구성·역할 정의, 명령창, 작업 체계·검수, 동시 작업 규칙, 전체 현황 홈(사용량 제외), 스튜디오, 팀원 상세, 보고서·문서함·피드백, 오류 대응, 중단·개입, 보안·활동 기록, 공통 지침·프로젝트 기억, 기본 알림, PC 프로그램 기본(트레이 상주·전역 단축키·OS 알림·절전 방지), CLI 연동(Claude Code·Codex) |
| 2차 | 편의와 완성도 | 시뮬레이션(B 방식: 체험판), 사용량 표시, 팀 템플릿, 작업 보드, 계획 승인 옵션, 전역 기억, 알림 세부 설정, 외부 내용의 출처·후속 작업 연결 기록, 대용량 파일 대응, PC 시작 시 자동 실행 |
| 3차 | 확장 | 시뮬레이션 A 방식(작업 사본 실행), 팀장급 중간 계층, 원격 접속·모바일 알림, 설치 파일·자동 업데이트 |

### 3.1 1차 내부 개발 순서

| 구간 | 먼저 확인할 범위 | 통과 기준 |
|---|---|---|
| 1차-A | 모의 에이전트, 작업·상태·메시지·정지·검수·병합 흐름 | 모의 시나리오로 지시부터 보고까지 완주하고 상태 전이·재시작 테스트 통과 |
| 1차-B | 실제 Claude Code·Codex 어댑터 | 각각 첫 턴·이어하기·이벤트 해석·실행 승인 바이패스·MCP 권한·하위 프로세스 종료를 실제 CLI로 검증 |
| 1차-C | 한 프로젝트의 실제 운영과 관리 화면 완성 | 실제 AI로 지시 → 작업 → 검수 → 병합 → 보고 → 수정 요청까지 통과 |

모의 에이전트를 가장 먼저 만들되, 실제 CLI 검증을 화면 완성 뒤로 미루지 않습니다. 1차의 기능 범위 자체는 위 표를 유지합니다.

## 4. 조직과 역할

### 4.1 조직 구조

```text
대표 (구글 로그인한 나)
└─ 메인 에이전트 (실행 계정의 PC 권한, 실행 권한 승인 바이패스)
   ├─ 스튜디오 · 프로젝트 A
   │  └─ 프로듀서 (필수 1명)
   │     ├─ 팀원 · 기획자 · Claude
   │     ├─ 팀원 · 개발자 · Codex
   │     └─ 팀원 · QA · Claude
   └─ 스튜디오 · 프로젝트 B
      └─ 프로듀서 (필수 1명)
         └─ 팀원 · …
```

| ORG-09 | 팀원 1명은 동시에 실행 중인 업무 1개만 가진다. 배정된 일반 작업은 하나씩 활성화하고 추가 작업은 대기열에 둔다. 관리 업무도 같은 팀원 안에서 직렬 실행한다 (5.7) | 1차 | 추가 (v0.5 결정) |

## 5. 작업 체계

일반적인 개발 회사의 업무 구조(요청 → 티켓 → 체크리스트, 코드 리뷰·QA를 거친 뒤 병합)를 그대로 따릅니다.

```text
지시 접수 → 계획(작업 쪼개기·배정) → 작업(각자 작업 공간) → 자동 검사 → 검수(리뷰·QA) → 병합 또는 산출물 확정 → 보고 → 대표 결과 승인
```

### 5.1 작업 단위

|---|---|---|---|---|
| 지시 | 요청·에픽 | 대표의 명령을 메인 에이전트가 등록 | 프로젝트(프로듀서) | 대표의 명령 1건 |

### 5.4 팀원 상태

작업 상태와 별개로, 팀원이 지금 무엇을 하고 있는지를 나타냅니다.

### 5.5 진행도 계산

| 대상 | 계산 |

### 5.7 동시 실행과 대기열

| 항목 | 확정 규칙 |
|---|---|
| 전체 상한 | 실행 중인 CLI 턴 N개, 기본 N=5. 메인 에이전트·프로듀서·일반 팀원 모두 포함 |
| 관리용 자리 | N이 2 이상이면 1자리를 관리 업무에 예약. 기본 5에서는 일반 작업 최대 4개. 관리 업무가 없더라도 일반 작업이 예약 자리를 차지하지 않음 |
| 관리 업무 | 메인 에이전트의 명령 처리·보고, 프로듀서의 계획·질문 응답·병합 판단, 배정된 검수자의 검수. 역할 이름만으로 분류하지 않고 프로그램이 업무 종류로 판정 |
| 관리 업무 동시 실행 | 전체 상한 안에서 빈 자리를 더 쓸 수 있으나 일반 작업 상한과 팀원별 중복 실행 금지를 유지 |
| N=1 설정 | 예약 자리는 없으며 관리 업무를 우선해 완전 직렬 실행. 이미 실행 중인 일반 턴을 자동 중단하지는 않음 |
| 팀원별 실행 | 팀원당 실행 중 업무 1개, 세션당 프로세스 1개. 다른 세션을 열어 같은 팀원이 동시에 일하도록 하지 않음 |
| 일반 작업 활성화 | 팀원에게 배정한 일반 작업은 하나씩 활성화. 기존 작업이 완료·취소·재배정되기 전에는 다음 일반 작업을 시작하지 않음 |
| 관리 업무 끼워 처리 | 기존 일반 작업의 턴이 끝난 뒤 질문 응답·타인 작업 검수 등을 처리할 수 있음. 별도 업무 세션에 연결하고 기존 작업 문맥과 섞지 않으며, 두 업무를 동시에 실행하지 않음 |
| 자리 반환 | 턴과 그 실행을 붙잡는 하위 명령의 종료를 확인한 뒤 반환. 답변·검수·사용량 한도 대기는 프로세스를 종료한 상태이면 자리를 사용하지 않음 |
| 우선순위 | 정지 제어는 대기열을 거치지 않고 즉시 처리. 실행 가능한 관리 업무를 먼저, 같은 분류에서는 작업 우선순위 → 대기 등록 시각 순으로 처리 |

관리 업무를 기다리는 팀원의 실행은 프로그램이 종료를 확인한 뒤 자리를 반환합니다. 해당 업무에 적용되는 긴급 정지·일시정지·보류 사유가 있으면 자리가 비어 있어도 시작하지 않습니다. 특정 작업의 답변 대기는 그 팀원의 다른 관리 업무까지 막지 않지만, 팀원·프로젝트 범위의 정지는 모든 소속 업무에 적용합니다. 같은 팀원의 업무를 바꿀 때는 팀원 실행 잠금과 세션 잠금을 함께 확인합니다.

### 7.1 병합·되돌리기 세부 규칙

| 항목 | 처리 |
|---|---|
| 검수 유효성 | 검사·검수에 사용한 작업 커밋 SHA와 기준 main SHA가 모두 현재 값과 같아야 함. 작업 폴더에 미반영 변경이 있으면 먼저 진행 상태로 돌림 |
| 긴 작업과 잠금 | 모델 검수나 충돌 해결을 기다리는 동안 main 잠금을 잡지 않음. 실제 main 변경 구간만 잠그고 바로 앞에서 버전을 다시 확인 |
| 병합 기록 | 작업별 병합 커밋을 남기고 main의 병합 전·후 SHA를 저장. 완료 기록 전 앱이 종료되어도 이미 반영됐는지 확인 가능해야 함 |
| 선택 되돌리기 | 대상 병합 커밋의 변경을 취소하는 새 커밋을 생성. main을 과거 시점으로 강제 이동하는 방식은 사용하지 않음 [T3] |
| 되돌리기 검수 | 되돌리기용 작업을 새로 만들어 검사·독립 검수 후 같은 main 잠금 절차로 적용. 원래 작업의 완료 이력은 유지하고 되돌리기 작업을 연결 |
| 충돌·의존성 | 뒤의 작업이 되돌릴 변경에 의존하거나 검사에 실패하면 보류. 어떤 작업까지 함께 조정할지 프로듀서가 계획하며, 이후 변경을 통째로 지우지 않음 |

## 10. 실행 정책과 활동 기록

대표 결정에 따라 **실행 권한 승인은 전면 바이패스**합니다. CLI의 파일·명령 실행을 위해 대표에게 허가를 받거나 실행 승인 대기로 멈추는 흐름은 두지 않습니다. 이는 작업 검수·결과 승인·선택적 계획 승인을 없앤다는 뜻이 아닙니다.

바이패스는 실행 계정에 없는 OS 권한을 새로 주지 않습니다. 앱은 자체 도구의 역할·대상·상태 조건과 git 처리 순서를 검사하지만, CLI가 직접 실행하는 파일·셸 접근을 worktree 안으로 강제 격리한다고 보장하지 않습니다. 아래의 역할 범위·민감 영역은 앱 업무 규칙이며 OS 접근 통제와 구분합니다. 실제 CLI 옵션은 15.5에 명시합니다.

### 10.1 역할별 업무 범위

| 주체 | 기본 파일·작업 범위 | 프로그램이 검사하는 요청 |
|---|---|---|
| 메인 에이전트 | 실행 계정이 접근할 수 있는 로컬 PC. 프로젝트·팀 구성·보고 총괄 | 프로젝트·팀원 관리, 지시·보고·기억 도구의 권한과 상태 |
| 프로듀서 | 담당 프로젝트. 공통 지침 수정은 변경형 작업 절차로 처리 | 작업 배정, 배정된 타인 작업의 검수, 독립 검수 후 병합 요청 |
| 팀원 | 자기 작업 폴더 변경, 담당 프로젝트 참고. 검수자는 고정된 대상 버전을 확인 | 자기 작업 단계·제출, 질문, 조건을 충족한 검수 결과 등록 |

작업 폴더 범위는 실행 위치와 앱 도구 검증으로 운영합니다. CLI 직접 접근에 대한 파일·네트워크 강제 차단을 완료 기준으로 요구하지 않습니다. 앱이 관측한 범위 이탈이나 예상하지 않은 main 변경은 기록하고 관련 작업을 보류합니다.

### 10.2 민감 영역

| 구분 | 관리 대상 | 취급 |
|---|---|---|
| 시스템 | Windows 시스템 폴더, macOS 시스템 폴더 등 | 실행 요청의 목적·대상·결과를 구분해 기록. OS가 거부하면 오류로 처리 |
| 개인 파일 | 프로젝트로 등록되지 않은 문서·사진·다운로드 폴더 등 | 지시와 관련된 작업 범위로 구분. 별도 대표 실행 승인 없음 |
| 비밀 정보 | .env, SSH·인증서 키, 클라우드 자격 증명, 브라우저 프로필 등 | 앱이 저장하는 로그·보고·화면 출력에 비밀 값 제거 적용 |

기존의 '보호 구역 접근 승인'과 '승인으로도 열 수 없음'이라는 보장은 사용하지 않습니다. 앱 도구의 거부와 임의의 로컬 프로세스 접근 차단은 같은 기능이 아닙니다.

## 15. PC 프로그램과 CLI 연동

욱채 프로그램은 대표의 PC에 설치해 쓰는 데스크톱 프로그램입니다. 프로그램이 내부에서 Claude Code CLI와 Codex CLI를 턴 단위로 실행하고(Claude Code는 `-p`, Codex는 `exec`, 다음 턴은 둘 다 resume), CLI가 내보내는 이벤트를 읽어 화면에 보여줍니다.

```text
욱채 프로그램 (PC)
├─ 화면 ─ 프로그램 창, 트레이 아이콘
├─ 오케스트레이터 ─ 턴·대기열, 작업·상태, 앱 도구 권한, 정지 제어, git 직렬 처리, 알림
├─ 앱 도구 서버(MCP) ─ 세션별 토큰으로 호출한 팀원 확인
└─ CLI 프로세스
   ├─ 메인 에이전트 ─ Claude Code 또는 Codex
   ├─ 프로듀서 ─ 프로젝트마다 1개
   └─ 팀원 ─ 맡은 작업이 있을 때만 실행
```

### 15.4 턴 진행과 바이패스 흐름

두 CLI 모두 한 번 실행이 한 턴입니다. 실행 승인은 기다리지 않으며 프로그램이 업무 상태와 정지 상태를 기준으로 다음 턴을 결정합니다.

```text
업무 배정 / 재개 가능 이벤트
 └→ 전역 정지·범위별 정지·보류·선행 작업 확인
     └→ 관리/일반 대기열 → 실행 자리·팀원 잠금·세션 잠금 확보
         └→ 첫 턴 또는 resume 실행 (매번 바이패스 설정 적용)
             └→ 턴·관련 하위 명령 종료 확인 → 자리 반환 → 프로그램 판정
                 ├─ 정지·취소 요청 있음 → 저장된 상태 유지, 다음 턴 시작 안 함
                 ├─ 검수 요청 → 자동 검사·버전 고정 후 검수자 관리 대기열
                 ├─ 질문 → 작업 보류(답변 대기), 답변 도착 후 조건 확인
                 ├─ 검수 통과 → 병합 대기열 또는 산출물 확정
                 ├─ 단계 남음 → '계속' 메시지를 같은 업무의 다음 턴으로 등록
                 ├─ 실행 여부 불명확 → 보류(복구 확인), 자동 재실행 안 함
                 └─ 오류 → 8장 규칙
```

| 상황 | 처리 |
|---|---|
| 파일·명령 실행 | CLI별 바이패스 설정으로 실행. 앱 실행 승인 대기 없음 |
| 검수 요청 | 작업자 턴을 마친 뒤 대상 버전을 고정하고 배정 검수자를 실행 |
| 프로듀서에게 질문 | 질문 ID·복귀 상태 저장, 해당 작업 보류, 팀원 프로세스 종료. 프로듀서는 관리용 자리에서 답변 |
| 대표의 직접 메시지 | 기존 턴·하위 프로세스 종료 후 같은 업무 세션에 우선 전달. 정지 상태면 메시지만 보관 |
| 대표 검수·결과 승인 | 앱 업무 화면에서 처리. CLI 실행 권한 승인이 아님 |
| 예상치 못한 CLI 승인 프롬프트 | 바이패스 설정·버전 불일치 오류로 처리. 승인 대리 실행 흐름을 새로 만들지 않음 |
| 재시작 | 정지·보류를 먼저 복원한 뒤 실행 결과 확인. 중복 실행이 없음을 확인한 업무만 대기열에 복원 |

앱 도구는 요청 ID를 가진 상태 변경을 즉시 저장한 뒤 결과를 응답합니다. 긴 응답 대기를 유지하지 않고 질문·검수 요청을 업무 이벤트로 등록해 턴을 끝내므로 관리 업무가 실행 자리를 확보할 수 있습니다.

### 15.5 구현 참고

아래는 권장 구성과 공식 문서로 확인한 CLI 옵션입니다. **설계 결정과 CLI 문서 확인을 구분**하며, 특정 설치 버전에서의 실제 실행 검증은 1차-B에서 수행합니다. 옵션·이벤트 형식이 바뀌면 어댑터별 검증 범위를 갱신합니다. 출처 [T1]–[T3]는 부록 C에 정리했습니다.

| 구성 요소 | 권장 |
|---|---|
| 프로그램 틀 | 기존 제안인 Electron + TypeScript를 유지. 설치 용량을 우선하면 Tauri를 별도 비교 |
| 화면 | React 등 웹 기술로 프로그램 창 구성 |
| 오케스트레이터 | 턴 실행·감시, 관리/일반 대기열, 팀원·세션 잠금, 상태 전이, 앱 도구 권한, 정지 복원, git 직렬 처리 |
| 앱 도구 서버 | 루프백 MCP 서버. 세션 토큰에 연결된 팀원·프로젝트·업무로 권한 검사 |
| 저장소 | SQLite(작업·상태·정지·요청 이력) + 파일(보고서·비밀 값을 가린 CLI 이벤트) |
| 하위 프로세스 종료 | Windows는 Job Object 등 프로세스 트리 관리, macOS는 프로세스 그룹 관리 방식 검증. 실제 자식·후손 프로세스 종료를 완료 기준으로 검사 |

| 항목 | Claude Code | Codex |
|---|---|---|
| 첫 턴 기본형 | `claude -p "메시지"` [T1] | `codex exec "메시지"` [T2] |
| 바이패스 옵션 | `--dangerously-skip-permissions`: 권한 확인 생략 [T1] | `--dangerously-bypass-approvals-and-sandbox`: 승인·샌드박스 바이패스 [T2] |
| 이벤트 읽기 | `--output-format stream-json --verbose` [T1] | `--json`으로 JSONL 이벤트 수신 [T2] |
| 다음 턴 기본형 | `claude -p --resume 세션ID "메시지"` [T1] | `codex exec resume 세션ID "메시지"` [T2] |
| 다음 턴 설정 | 첫 턴과 동일한 바이패스·MCP·지침·실행 위치를 다시 적용. 시작 시 유효 설정 확인 | 같음. `exec`와 `exec resume`의 옵션 위치·지원 여부는 설치 버전별로 검증 |
| 지침·앱 도구 | 역할 지침 및 앱 규칙을 실행 설정으로 전달하고 MCP 서버 연결 | 공통 지침·업무 메시지와 MCP 설정 사용 |
| 승인 응답 | 앱 승인 도구·승인 대기 응답을 연결하지 않음 | 앱 승인 도구·승인 후 대리 실행을 연결하지 않음 |

| 네트워크 | 바이패스 설정을 외부 전송 차단 기능으로 설명하지 않음 | 같음 |
| 진행도·사용량 | 실제 이벤트에서 제공되는 항목만 표시. 단계 완료는 앱 보고 도구가 기준 | 같음 |

**첫 턴 실행 예시** — 모델·노력치·MCP·역할 지침·실행 위치는 어댑터에서 별도로 설정합니다. 아래 두 줄은 실제 실행 테스트를 마친 명령으로 제시하는 것이 아니라 공식 옵션을 조합한 구현 참고입니다. [T1][T2]

```text
claude -p --dangerously-skip-permissions --output-format stream-json --verbose "작업 메시지"
codex exec --dangerously-bypass-approvals-and-sandbox --json "작업 메시지"
```

| 환경 | 1차 적용 | 검증 항목 |
|---|---|---|
| Windows + Claude Code | 네이티브 CLI 우선 | 첫 턴·resume, 권한 확인 생략, MCP, 이벤트·종료 |
| Windows + Codex | 네이티브 CLI 우선, 프로젝트는 Windows 드라이브 | 첫 턴·resume, 바이패스, MCP, 이벤트·종료 |
| macOS + 각 CLI | 지원 목표, 별도 실기 통과 후 지원 완료 | 같은 항목과 프로세스 그룹 종료 |
| WSL | 현재 우선 검증 범위 밖 | 검증 전 지원 완료로 표시하지 않음 |

OS의 권한 거부·인증 실패·외부 서비스 정책에 의한 실패는 실행 오류로 보고하며, 앱이 이를 권한 상승이나 자동 승인으로 해결했다고 표시하지 않습니다.

## 부록 B. 원본 메모

원본 메모는 수정하지 않고 보관합니다. 현재 적용 규칙과 다른 표현(예: 세션 1개 = 팀원 1명)은 본문의 v0.5 결정이 우선합니다.

```text
로그인 방식 구글
구글로그인 한 내가 대표

기본 시스템 구조 
1. 왼쪽에 탭이 있고, 프로젝트 별로 스튜디오를 볼 수 있음(각 스튜디오 팀원은 어떻게 구성되어 있고(ai종류 및 노력치), 각 팀원이 맡은 역할은 뭔지 볼 수 있음)
2. 팀원들이 지금 업무중인지 아닌지 시각적으로 볼 수 있음
  2-1. 작업 중이면 무슨 작업을 작업중인지 얼마나 진행됐는지 진행도도 볼 수 있음
3. 왼쪽 탭은 프로젝트, 문서함, 시뮬레이션, 운영 설정 이렇게 4개 탭이 존재

1. 메인 에이전트
- 로컬 pc의 모든 권한을 가짐
- 해당 프로젝트의 팀원을 얼마든지 추가 및 삭제할 수 있음(팀원은 코덱스, 클로드 각 세션1개가 1명의 팀원)
   > 한 프로젝트당 프로듀서 에이전트 1개는 무조건 필수 
   > 계층적 구조 형태로 팀을 짜고, 프로듀서가 메인 에이전트에게 최종 전달하면 메인 에이전트가 정리 후 대표(나)에게 전달
	>> 전달한 문서는 프로젝트별로 정리되어 있어 내가 언제든시 필요시마다 볼 수 있음
- 대표는 메인 에이전트에게 프로젝트를 선택(리스트바)해서 명령을 전달함
- 자동으로 작동하는 스킬 알아서 발동할테니 놔두고(발동 안하면 이것도 수동으로 처리 강제할 필요는 없음), 수동으로 발동시켜야 하는 스킬의 경우 메인에이전트 판단하에 하위 프로젝트 팀원들에게 스킬을 사용해서 업무를 지시함
- 대표가 작업 지시 시 예상 결과를 시뮬레이션 가능하도록 따로 만듬 
    > 시뮬레이션 탭에서는 프로젝트별로 현재 작업중인 작업이 끝낫을 경우의 결과를 시뮬레이션 형태로 짧막하게 플레이 해볼 수 있음 당연 해당 프로젝트의 ui가 직접 사용 되어야함
```
